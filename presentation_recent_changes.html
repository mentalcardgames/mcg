Architecture Concurrency & Lifecycle

Builder & Handle Pattern in Backend Concurrency

Decoupling async network I/O from synchronous deterministic state updates

Key Innovations

  • Synchronous Controller Thread: Game updates and poker logic run in a dedicated OS thread without mutex locking or async runtime starvation.
  • Staged Lifecycle: build() resolves ports, validates paths, and allocates channels without starting tasks. spawn() launches Tokio background tasks and the Controller thread, returning handles.
  • Strongly Typed Handles: ControllerHandle, NetworkHandle, and BackendHandle act as cloneable MPSC message proxies across execution boundaries.
  • Graceful Shutdown: Clean termination of Iroh QUIC endpoints, WebSocket listeners, bot tasks, and thread joining without orphan processes.

P2P Networking Local Multi-Node Testing

Multi-Instance P2P & Ephemeral Identities

Solving the local pairing obstacle: dynamic ports & non-persisted Iroh keys

The Challenge & Solution

The Problem: An Iroh P2P endpoint cannot connect to itself. When testing locally, two server instances running on the same machine would collide on port 3000 and share the same persisted identity key in mcg-server.toml.

  • Dynamic Port Discovery: Backend scans from port 3000 upward (e.g. 3001, 3002), or honors --port and --strict-port.
  • --ephemeral CLI Flag: Generates a transient in-memory Iroh secret key, ensuring a unique Node ID without writing to disk.
  • P2P Deduplication: NetworkSupervisor automatically resolves bidirectional connection races deterministically by Node ID comparison.

Section 2

Core Architecture: The Builder & Handle Pattern

In previous iterations, the backend maintained a shared monolithic AppState protected by coarse-grained mutexes. This created contention between incoming WebSocket connections, internal bot drivers, and the card game engine.

The new architecture separates execution into two distinct environments:

  • Synchronous Controller Core: Executes on a dedicated OS thread. It processes game state changes deterministically without async task starvation or locks.
  • Asynchronous NetworkSupervisor: Runs on the Tokio runtime, managing Axum HTTP/WebSocket listeners, Iroh QUIC connections, and peer deduplication.
  • Builder Pattern (build() vs spawn()): Separates resource discovery (port scanning, channel allocation) from runtime execution.
  • Handles: ControllerHandle, NetworkHandle, and BackendHandle provide cloneable, typed MPSC communication channels across thread boundaries.
Section 3

Monorepo Restructuring & crates/poker Extraction

Game logic, betting structures, and bot simulations were previously coupled directly to the native server executable. This sprint cleanly extracted all poker-specific algorithms into crates/poker (mcg-poker).

Furthermore, the workspace folder structure was completely normalized: all packages now reside under the top-level crates/ directory (including crates/frontend, crates/native_mcg, crates/shared, crates/qr_comm, crates/engine, and crates/cardgame_dsl). Root configuration files were cleaned up, moving package-specific release profiles directly into their respective crates.

Section 4

Multi-Instance Testing & Ephemeral Identities

A major bottleneck for local peer-to-peer development was identity collision. Because Iroh QUIC nodes cannot connect to themselves, running two local instances previously caused connection aborts because both loaded the same secret key from mcg-server.toml.

Two key features solved this:

  • Dynamic Port Hunting: If port 3000 is taken, the backend automatically binds to 3001, 3002, etc. Strict port binding can be enforced via --strict-port.
  • The --ephemeral CLI Flag: Generates a disposable, in-memory Iroh keypair without touching disk files. Developers can now run just backend in Terminal 1 and just backend --ephemeral in Terminal 2, allowing immediate local QR/ticket connection testing.
Section 5

Dynamic Origin & Real-Time Client Synchronization

The WebAssembly frontend previously hardcoded its backend connection to 127.0.0.1:3000. This prevented seamless access across mobile devices, alternate ports, or secure HTTPS origins. The frontend now inspects web_sys::window().location() at runtime to dynamically derive the host and correctly select ws:// or wss://.

Additionally, new protocol messages (PlayerSetup, UpdatePlayerSetup, and RequestPlayerSetup) were added. When any player or server updates game configurations, all open browser tabs reflect the updated active player, seat configuration, and state immediately.

Section 6

Cross-Platform Tooling & Unified CI/CD

The repository's justfile was overhauled with dedicated [windows] and [unix] implementations. Windows users can now run background tasks (just backend-bg) and pass arbitrary CLI arguments without escaping errors.

A unified CI suite provides single-command verification:

  • just ci: Executes format checking, clippy (with strict -D warnings), and tests across all crates, including headless Chrome tests for WebAssembly.
  • Crate-level filters: just test poker, just clippy frontend, just fmt-check shared.
Section 7

Documentation Submodule & Live Site

The documentation was decoupled into an independent Git submodule, enabling continuous deployment of the official documentation website at https://mentalcardgames.github.io/.

Key documentation additions include the 5-player split-node ring topology diagram, comprehensive developer onboarding instructions, local multi-instance testing guides, and detailed specifications of the Builder and Handle concurrency models.
